## 1. 最終的に作りたいもの

- おもちゃの赤色可視レーザー銃をディスプレイに向けて撃ち、外付けWebカメラでディスプレイを撮影し、ブラウザのWebアプリ（フロントエンド完結）で着弾点を検出して、画面上のターゲットに当たったらアニメーションを返すゲーム。
- レーザーは「少なくともカメラで捉えられるレベルで赤く、細く、強い」可視光が前提。赤外線方式ではない。
- 現在はゲーム本体ではなく、**補正と検出の技術を実機パターンで振って絞り込むための検証PoC** の段階。ゲーム化（ターゲットやアニメーションの作り込み）は方式が固まってから。

## 2. 調査で分かったこと（設計の前提）

2026-10-30 に出典付きの深掘り調査を実施した。要点のみ記す。詳細な数値や出典URLが必要な場合は、本節の末尾の参考リンクを辿ること。

- **条件付きで実現可能**。固定カメラで画面を撮り、レーザー点を色で検出して画面座標へ写す方式自体は、研究・学生プロジェクト・商用ドライファイア製品で繰り返し実証されている。
- **最大のボトルネックは幾何ではなく「時間対応付け」と「カメラの自動制御」**。表示→カメラ取得の遅延は、方法が明記された loopback 実測例で平均87.2ms（77〜99ms、30fpsで約2.6フレーム）。遅延は環境依存が大きいので、一般値を決め打ちせず自機で実測する前提で設計すること（設計レンジは50〜200ms）。
- **「理想画像とのピクセル差分を主方式にする」設計は非推奨**。自動露出/ホワイトバランス、ガンマ、モアレ、LCDリフレッシュとローリングシャッター、解像度差、環境反射のため、カメラ画像はアプリが描画した画像とピクセル単位で一致しない。差分は補助信号に回し、主方式は「画面領域（ROI）を正面化し、赤色度＋輝度飽和＋直前フレームとの時間差分の複合条件で blob 重心を取る」こと。強いレーザー点は中心が白飛びし周囲に赤いハローが出る点にも注意（「一番赤い点」だけを探すと取りこぼす）。
- 幾何はホモグラフィ（4点射影変換）でまず十分。レンズ歪み補正は、広角カメラを近距離・斜めで使い、画面の縁で系統誤差が支配的と判明した場合にだけ段階導入する。
- マーカーを使う場合の本命は **AprilTag（WASM版、小数ピクセルのコーナーが返る）か js-aruco2（ArUco）**。QRコード系（jsQR/ZXing/zbar）は「内容を読む」ための設計で、複数同時検出やサブピクセル精度が要る幾何キャリブレーションには不適。
- マーカー配置は、較正時のみ画面内に大きく表示し、ゲーム中は隅の小マーカーだけ残してドリフト監視する折衷案が推奨。物理マーカーを画面の隅の真隣に貼るだけの方式は、画面外からの外挿になるうえ貼付誤差がそのまま系統誤差になるため単独では推奨しない。
- トラックの制約（露出・WB・フォーカスの固定）は `applyConstraints` で試行できるが、効くかどうかはブラウザ/OS/カメラドライバ依存。`getCapabilities()` / `getSettings()` で検証し、効かない環境では色度正規化で耐えるフォールバックを前提にすること。`requestVideoFrameCallback` の `captureTime` は仕様上 optional で、返る保証はない。
- 描画側は、2Dターゲットなら Three.js より PixiJS / Canvas2D が軽いというのが調査結論（ゲーム化フェーズの話であり、PoC本体は vanilla 構成のまま）。

裏取りできなかったもの（根拠として使わないこと）:

- 参考として提示された flukeforest.jp の2製品（FF-SG01 / FF-SG02）は技術記事ではなく販売ページで、方式も不可視赤外線＋専用TVアダプター内蔵チップであり、本プロジェクトの根拠にはならない（「画面位置を認識して着弾判定する商用製品が存在する」傍証のみ）。

## 3. 現在の実装状態

### 実装済み（このブランチ）

- `index.html` / `main.ts` / `style.css` の vanilla 構成。元は単体HTMLの検証ページで、リポジトリの lint（markuplint / Biome）を通すために script/style を分離した。挙動・機能は移植前と同一。
- 検出方式6種を同じ映像に同時実行して比較できる（単純RGB / HSV赤 / 輝度飽和 / 時間差分 / 理想差分（実験扱い） / 複合（推奨））。方式ごとにマスク・検出座標・処理時間を表示。
- 補正トグル: ホモグラフィ正面化、ぼかし、色度正規化、背景EMA差分。パラメータ8種を即時変更可能。
- 入力2系統: 実カメラ（`getUserMedia`、露出/WB固定の試行と capabilities/settings 表示、`requestVideoFrameCallback` のメタデータ表示）と、模擬カメラ（画面を斜めから撮った合成映像＋模擬レーザー。カメラ無しでも検証を始められる）。
- 手動4点キャリブレーション（カメラ映像上で画面四隅をクリック）→ ホモグラフィ算出 → 正面化ビュー。
- テストパターン7種（格子5×4、移動ターゲット、白画面、赤多め、同期カウンタ等）、悪条件シミュレーション（露出揺れ・反射・ノイズ）。
- 格子点での位置誤差を自動記録（px / 画面対角比%、目安として対角比1.5%未満かを表示）し、測定結果をJSONでダウンロードできる。
- 登録済み: `vite.config.ts` のMPA入力、`src/index.html` の目次、ルート `README.md` のプロジェクト節。

### 検証の状態

- `npm run check`（markuplint + Biome）成功、`npm run build`（tsc && vite build）成功、`dist/laser-detection-poc/` の生成を確認済み。
- 動作確認は**模擬カメラのみ**（監査環境のプローブで、キャリブレーション→正面化→複合方式でのヒット記録、格子誤差の自動記録まで確認）。模擬映像で出た数値（例: 誤差7px・対角比0.59%）は実レーザーの精度ではない。
- **実カメラ経路は実機未検証**。検証環境にカメラが無いため、エラー時のフォールバック表示のみ確認済み。実機で初めて分かる項目: 露出/WB固定が効くか、`captureTime` が返るか、実際の遅延と誤差。
- PR #620 の追加行については個人情報チェック済み（メールアドレス・実名・ローカルパス・秘密情報・識別子らしい文字列なし。外部URLは公開情報への参照のみ）。
- Jest テストは未実施（新規コードは現状テスト対象外）。

### 実装上の保留・制約

- `main.ts` は `// @ts-nocheck` で型の厳密化を保留中（移植元の挙動を変えないことを優先したため）。一部の Biome ルールにも理由付きで `biome-ignore` がある。**検出方式が固まった段階で型付けと構造整理を行う**想定。
- OpenCV.js は未導入。歪み補正や ChArUco 較正が必要になった場合も、常駐させず較正時のみ遅延ロードする方針。
- マーカー自動検出（AprilTag / ArUco）は未実装。現在は手動4点のみ。
- 実カメラには secure context が必須。このリポジトリの GitHub Pages（https）か `http://localhost` で開くこと。Muse のアーティファクト表示枠内では secure context にならず実カメラが使えなかったことが、こちらへ移設した理由。
