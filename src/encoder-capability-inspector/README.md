# エンコーダー実用可否検査 (Encoder Capability Inspector)

ブラウザー・OS・GPU・ドライバー・エンコーダー実装の組み合わせごとに異なる、映像・音声エンコード設定の
**実用可否**を利用者自身が確認するための WebCodecs ツール。

`VideoEncoder.isConfigSupported()` が `true` を返すことと、その設定で実際に使えることは別物である。
このツールは宣言的な対応判定で止めず、候補ごとに次をすべて通す。

1. 設定が受理されるか（`isConfigSupported`）
2. 実際にエンコード出力が生成されるか
3. 出力をデコードできるか
4. 想定コンテナへ多重化できるか
5. 出力が異常に小さい・空でないか
6. 処理時間が要求フレームレートに対して実用的か

結果は「この環境でその設定が一度実出力まで到達した」ことを示すものであり、
すべての録画条件での恒久的な成功を保証するものではない。

## 検査対象

| 種別 | 内容 | 候補数 |
| --- | --- | --- |
| 映像 | H.264 / H.265 / VP9 / AV1 / VP8 を Profile・Level・ビット深度まで展開した 154 個の codec string × ハードウェア方針 3 種 | 462 |
| 音声 | AAC / Opus × 1ch・2ch × 各ビットレート（48 kHz） | 22 |
| | **合計** | **484** |

同じ codec string でも `prefer-hardware` / `no-preference` / `prefer-software` で結果が割れるため、
方針ごとに別の候補として検査する。10bit・4:2:2・4:4:4・Level 6.x などは `experimental` として
区別し、ファミリー要約の分母から除く。

各候補の解像度・FPS・ビットレートは、その Level が本来想定する上限に近い値を使う。
「その Level を名乗る設定がその負荷を捌けるか」を見るための条件であって、実録画の推奨設定ではない。

## 2 種類の検査

### 一括実用検査 (Full capability inspection)

484 候補すべてを 2 フレーム（音声は 2 チャンク）で通す。
候補ごとの可否を洗い出すのが目的なので、必要最小限の入力しか作らない。

参考: Apple Silicon Mac + Chromium で待機 0ms のとき全 484 候補が **約 40 秒**。
Windows + Chromium + NVIDIA で **約 53 秒**。

### 実用継続検査 (Sustained load test)

一括実用検査のあと、選択した候補だけを指定秒数ぶん流し続け、実効 FPS と
フレーム予算に対する処理割合を測る。単発の少数フレームでは分からない継続性能を見るためのもの。

検査時間に上限は設けていない。長く回したいのは正当な使い方で、中断はいつでも効く。
ただしデコード検証と多重化のために 1 候補ぶんの出力を最後まで抱えるので、長く回すとメモリは伸びる。
候補は 1 件ずつ処理して都度解放するため、山になるのは「いちばんビットレートの高い候補 1 件ぶん」で、
選択した全候補の合計ではない。見積りが大きいときは実行前に注意を出す。

入力は 2 モード。

- **合成パターン**: 再現可能な性能検査
- **画面・タブのキャプチャ**: `getDisplayMedia` + `MediaStreamTrackProcessor` で実映像・実音声を流す。
  **録画ファイルは一切作成しない。**

実効 FPS が要求 FPS の 75% を下回ると、成功でも警告として記録する。

#### キャプチャ音声の扱い

共有ダイアログで音声を共有すると、音声候補もキャプチャした実音声で検査できる。
共有しなかった場合、音声候補を選んでいると `live-capture-audio-track-unavailable` で止まる。

`AudioEncoder` は設定どおりのサンプルレートとチャンネル数の `AudioData` しか受け取らないので、
チャンネルの割り当てと線形補間のリサンプルを挟んで形を合わせる（[workers/liveAudio.ts](workers/liveAudio.ts)）。
音質のためではなく、環境が違っても検査を通すための処置。

音声処理（エコーキャンセル・ノイズ抑制・自動ゲイン）を有効にすると、処理系がモノラル前提のために
トラックが 1ch へ落ちてくることがある。そのため制約ですべて切ってから要求する。
ただしこれで必ず 2ch になるわけではない（共有元が本当にモノラルのこともある）。
実際に何 ch で取れたかは `getSettings()` で確かめ、結果へ残す。
2ch 候補を 1ch のキャプチャで通した場合は複製で形を合わせたうえで
`live-audio-captured-as-mono` を警告として記録する。エンコードは通るが、
2ch を実際に扱えたことの確認にはならないため。

## 合成パターン

2 種類の検査は入力に求めるものが違うので、パターンも 2 系統に分ける
（[domain/synthetic.ts](domain/synthetic.ts)）。

| | 一括実用検査 | 実用継続検査 |
| --- | --- | --- |
| 映像 | 1 枚を作って全フレームで使い回す | フレームごとに作り直す |
| 音声 | 1 チャンクを作って繰り返す | チャンクごとに作り直す |
| 狙い | 生成負荷を検査へ持ち込まない | 圧縮が効きすぎない絵と音にする |

一括実用検査は 484 候補を 1 周するので、入力生成は軽いほど結果が揺れない。
一方、実用継続検査で単色の静止画や単一の正弦波を流すと、圧縮が効きすぎてエンコーダーの実力が測れない。
実用継続検査のパターンには、色相が回る背景・横スクロールする縞・速度の違う矩形・移動するノイズタイルと、
多重波形の対数掃引・振幅掃引・微小ノイズを入れてある。

計測にあたっては、入力の用意にかかった時間（合成パターンの生成、ライブフレームの拡縮）を
`processingMs` から差し引く。実際の録画では既にできているフレームが渡ってくるので、
検査治具の都合をエンコーダーの実力に混ぜない。

パターンはすべてフレーム番号・サンプル位置から決まるので、何度実行しても同じ列が出る。
乱数はシード付きの線形合同法で、`Math.random` は使わない。

### 目と耳で確かめる

アプリ上の「合成パターンを確認」（既定は折りたたみ）で、検査へ渡すのと同じ生成コードから
映像を再生し、音声を波形付きで鳴らせる。検査の実行中は止まる。

ファイルとしても書き出せる。出力は [samples](samples) に置いて git 管理する。

```bash
npm run inspector:samples        # 生成しなおす
npm run inspector:samples:check  # 現在のパターンと一致しているか確かめる
```

- `video/compatibility.png`: 一括実用検査の 1 枚
- `video/sustained.png`: 実用継続検査の動き（APNG。ブラウザーでそのまま再生される）
- `audio/*.wav`: 48kHz/16bit
- `manifest.json`: 生成条件と、圧縮前の生データの SHA-256

書き出しは Node の `zlib` だけで PNG / APNG / WAV を組み立てる（[scripts](scripts)）。
ffmpeg も追加の依存も要らない。`--check` は生データのハッシュだけを見るので、
zlib の実装差でファイルのバイト列が変わっても誤検出しない。

Canvas 側と Node 側で同じ画素になるよう、描画命令は整数座標の矩形塗りとタイルの等倍貼りだけに限り、
色は `hsl()` 文字列を経由せず RGB の整数で持つ。

## 使い方

```bash
npm run dev
```

`http://localhost:5173/encoder-capability-inspector/index.html` を開き、「一括実用検査を開始」。

- 結果は検査終了を待たず、候補が完了するたびに一覧へ積まれる
- 「検査を一時中断」でいつでも止められる。ここまでの結果は残り、「途中から再開」で残りの候補から続けられる
- 実用継続検査の中断には再開機構が無い。完了したぶんの結果だけが残る
- 「結果を破棄」で保存済みレポートを消す
- 候補間の待機は既定 0ms。0 のときはタイマーを一切張らず、待機処理そのものを省く

UI は日本語と英語に対応している。右上のトグルで切り替えられ、初期表示はブラウザーの言語設定から決まる。

### 結果一覧の見方

列は「一括実用検査のフレーム予算」と「実用継続検査」を分けてある。前者は全候補が持ち、後者は
実用継続検査を実行した候補だけが持つ値なので、同じ列に重ねると比較しづらい。

各列の見出しは絞り込みと並べ替えの両方を兼ねる。

- 絞り込みはその列の値だけを見る。しきい値の選択肢は 100% 超 / 100% 以下のように必ず対になっている
- 実用継続検査列の 100% 超 / 100% 以下は、未実施の候補を含めない。未実施は予算比 0 なので、
  しきい値だけで見ると「100% 以下」に紛れてしまう
- 見出しを押すと 昇順 → 降順 → 解除 と一巡する。解除すると「新しい候補が先頭」の既定の並びへ戻る。
  押せることが伝わるよう、未ソートの列にも中立の矢印を薄く出している
- ファミリー列には映像・音声のアイコンを添える。`H.264` と `Opus` が同じ列に並ぶため、
  名前だけではどちらの検査か読み取れない。並べ替えも種別でまとめてから行う

実験的な構成（10bit・4:2:2・4:4:4・上位 Profile・Level 6.x）は codec string の隣にバッジを出し、
理由をツールチップに書く。一覧の上のトグルで「すべて / 実用構成のみ / 実験的のみ」を切り替えられる。

### 詳細列

失敗・警告は 2 行で出す。上がワーカーの返したコードそのもの、下がその解釈。

```
Flushing error.
設定は受理されたが output で失敗

isConfigSupported-false
この設定は宣言の時点で拒否されました
```

コードは環境をまたいで報告・検索されるものなので、訳文に置き換えず必ず残す。
訳を持たないもの（デコーダーが返す生のメッセージ、タイムアウト）は上の行にだけ出る。

### フレーム予算の読み方

一括実用検査は 2 フレームだけの互換性確認なので、フレーム予算比には初期化のコストがそのまま乗る。
**100% を超えていても実用上の問題を意味しない。** 継続的な性能は実用継続検査の値で判断する。
この断りは一覧の上と、フレーム予算列の見出しのツールチップに出している。

### no-preference が実際にどちらで動いたか

WebCodecs には「実際に使われた実装」を返す API が無い。`isConfigSupported` が返す設定にも、
要求した `hardwareAcceleration` がそのまま入るだけで実体は分からない。

そこで同じ codec string の `prefer-hardware` / `prefer-software` と出力を突き合わせて**推定**する
（[domain/backendInference.ts](domain/backendInference.ts)）。合成入力は決定的なので、実装が同じなら
出力バイト数とチャンク数も一致する。

判定はどちらも「出力が完全に一致した」ことを条件にする。根拠の強さは変わらない。

- 両方の方針が成功して出力が割れているなら、一致したほうを実体とみなす
- 片方の方針が失敗しているなら動く実装はもう一方しか無い。そのうえで出力も一致すれば、
  消去法と一致の両方が揃うので同じく実体とみなす
- 出力が一致しないなら、どちらでもない実装が動いたことになるので寄せない
- 両方の方針の出力が同じなら、方針を変えても実装が変わらなかったということで区別できない

いずれも判定できないときは「実体不明」とする。方針欄には `≈ HW` のような短い印だけを出し、
根拠と方法はツールチップへ回す（列幅に文章を置くと省略記号で切れて何も読み取れない）。

入力が違えば出力も変わるため、突き合わせるのは合成入力の一括実用検査の結果だけに限る。
あくまで推定であって、断定はできない。

参考: Windows + Chromium + NVIDIA では 154 個の codec string のうち、
HW 29 件・SW 43 件と判定でき、残る 82 件は no-preference 自体が失敗して判定材料が無かった。
「出力が同じで区別できない」「どちらとも一致しない」はどちらも 0 件だった。

### ファミリー要約

ファミリーで一律に可否を決めず、「具体的な設定のうち何件が通ったか」を数える。
映像と音声で数え方が違うので、段を分けて出す。

- 映像は codec string 単位。ハードウェア方針が違っても 1 件として数える
- 音声は候補単位。AAC はどのビットレート・チャンネル数でも codec string が `mp4a.40.2` のままで、
  codec string では設定を区別できない

既定では実験的な構成を分母から除く。対応が期待しにくい構成で割合が下がると実態を読み違えるため。
分母に含めるかはチェックボックスで切り替えられる。

### 結果の書き出し

「結果をJSONで保存」で、全結果と実行環境の概要を書き出せる。環境をまたいで突き合わせたり、
報告に添えたりするためのもの。

`previousCompleted` は落とす（直前の完全レポートを丸ごと抱えているので、外へ出すと二重になる）。
画面内容・音声サンプル・デバイス固有 ID は元々レポートに入れていない。
ブラウザー・OS・GPU の概要は入るので、共有するときはそのつもりで。

### 参考文献

codec string の書き方や、この検査が何を確かめているのかを追える資料を
[features/References](features/References) にまとめてある。既定では畳んである。

## 設計上の要点

### メインスレッドを止めない

映像生成・エンコード・デコード・多重化はすべて専用ワーカー（[workers/inspectionWorker.ts](workers/inspectionWorker.ts)）で行う。
UI 側は候補を 1 つずつ投げて進捗を受け取るだけ。

進行中のステージ更新では結果配列の参照を差し替えないため、484 行の一覧は再描画されない。
行は `@tanstack/react-virtual` で仮想化し、DOM 上の行数を表示範囲ぶんに抑える。
結果は新しいものから先頭に積まれるので、利用者がスクロール中なら挿入ぶんだけ位置を補正する。
並べ替え中は行がどこに入るか分からないため、この補正は行わない。

### 経過時間は実働で数える

中断して再開できる以上、最初に開始した時刻からの経過には「止まっていた時間」が入ってしまう。
そこでレポートは実際に検査していた時間の累計（`activeMs`）を持ち、経過表示と残り見込みはこれを使う。
`activeMs` は `updatedAt` の時点までの値なので、実行中の表示はそこからの差分を足して出す。
実用継続検査を回しているあいだは一括検査の時計を進めない。

### 保存は終端状態だけ

実行中の結果はメモリ（jotai）にだけ置き、IndexedDB へ書くのは `complete` / `cancelled` / `failed` に
達したときだけ。候補ごとに 484 件ぶんのレポートを書き戻すとシリアライズだけで詰まる。

完全に完了したレポートは `previousCompleted` として 1 段だけ引き継ぐ。
再検査を途中で中断しても、直前の完全な結果が壊れない。

保存するのは設定値・成否・計測値・環境の概要のみ。
画面内容・音声サンプル・デバイス固有 ID は保存しない。

### 排他

同時に複数の検査を走らせないよう Web Locks で排他する。オリジン単位なので複数タブでも 1 つしか通らない。
保存済みレポートの更新は BroadcastChannel で他タブへ伝える。

### 失敗コードの扱い

ワーカーが返す失敗・警告は `isConfigSupported-false` のようなコードで、レポートにもそのまま保存する。
表示時に [locales](locales) の説明文へ置き換えるが、環境をまたいで報告・検索できるようコードも括弧で残す。
訳を持たないもの（デコーダーが返す生のメッセージ、タイムアウト）はそのまま出す。

詳細列の絞り込みは訳文とコードのどちらでも引ける。
言語に依存しない [domain/filters.ts](domain/filters.ts) には照合用の文字列を関数で渡している。

## 元仕様との差分

この機能はもともと Chrome 拡張（録画アプリ）の一部として書いたものを、
拡張 API に依存しない独立した Web アプリとして書き直したもの。

元の仕様書のうち、**3.6「録画設定への反映」と 3.7「録画時の再検証」は対象外**とした。
このリポジトリには録画機能そのものが無く、検査結果を反映する先が存在しないため。
そのため次は実装していない。

- 検査結果による録画設定のコーデック選択のゲーティング
- 録画開始直前の、実際の録画条件（解像度・FPS・ビットレート・音声ch・コンテナ）での再検証
- 録画開始要求による検査の自動停止、録画中の検査開始禁止

一方、元実装で未達だった**音声候補の多重化**（仕様 3.1-4）はこちらで実装した。
AAC は mp4、Opus は webm へ実際に書き出して検証する。

## テスト

```bash
npm run test:ci
```

WebCodecs は Node で動かないため、単体テストの対象は純粋関数のみ。

- [domain/plan.test.ts](domain/plan.test.ts): 候補行列の件数・ID の一意性・codec string の形式
- [domain/synthetic.test.ts](domain/synthetic.test.ts): 合成パターンの決定性・位相の連続・クリップしないこと
- [workers/liveAudio.test.ts](workers/liveAudio.test.ts): キャプチャ音声のチャンネル割り当て・リサンプル・詰め替え
- [domain/report.test.ts](domain/report.test.ts): 完了判定・`previousCompleted` フォールバック・ファミリー集計
- [domain/filters.test.ts](domain/filters.test.ts): 絞り込み述語
- [domain/backendInference.test.ts](domain/backendInference.test.ts): `no-preference` の実体推定
- [domain/sustained.test.ts](domain/sustained.test.ts): 実用継続検査が抱えるメモリの見積り
- [domain/export.test.ts](domain/export.test.ts): 書き出しの封筒と持ち出さない項目
- [utils/preferences.test.ts](utils/preferences.test.ts): 設定値の検証

エンコード・デコード・多重化の実処理はブラウザーでの手動確認による。
