# 検査の使い方と入力

## 2 種類の検査

### 一括実用検査 (Full capability inspection)

1,406 候補すべてを通す。映像は 2 フレーム、音声はエンコーダーの先読みを越える量を入力する。AAC は 1024 samples を 6 チャンク、Opus は 960 samples を 4 チャンク供給する。候補ごとの可否を洗い出す検査だが、`flush()` に必要なサンプルが不足して偽陰性にならないよう、通常出力に必要な量のおよそ二倍を使う。

各候補では次をすべて確認する。

1. 設定が `isConfigSupported` で受理されること
2. エンコーダーが実際に出力を生成すること
3. 出力をデコードできること
4. 想定コンテナへ多重化できること
5. 出力が空、または異常に小さくないこと
6. 処理時間が要求フレームレートに対して実用的であること

参考時間は実行環境・エンコーダー実装・候補ごとに大きく変わる。特に音声は、プロファイルを実出力で照合するため `isConfigSupported()` だけの検査より時間がかかる。

### 実用継続検査 (Sustained load test)

一括実用検査のあと、選択した候補だけを指定秒数ぶん流し続け、実効 FPS とフレーム予算に対する処理割合を測る。単発の少数フレームでは分からない継続性能を見るためのもの。

検査時間に上限は設けない。候補は 1 件ずつ処理して都度解放するが、デコード検証と多重化のために 1 候補ぶんの出力を最後まで保持する。長時間・高ビットレートではメモリ見積りの警告を確認する。実効 FPS が要求 FPS の 75% を下回ると、成功でも警告として記録する。

## 入力モード

- **合成パターン**: 再現可能な性能検査。入力生成は [../domain/synthetic.ts](../domain/synthetic.ts) にある。
- **画面・タブのキャプチャ**: `getDisplayMedia` と `MediaStreamTrackProcessor` で実映像・実音声を流す。録画ファイルは一切作成しない。

### 合成パターン

一括実用検査と実用継続検査では入力へ求めるものが違うため、パターンを 2 系統に分ける。

| | 一括実用検査 | 実用継続検査 |
| --- | --- | --- |
| 映像 | 1 枚を作って全フレームで使い回す | フレームごとに作り直す |
| 音声 | 1 チャンクを作って繰り返す | チャンクごとに作り直す |
| 狙い | 生成負荷を検査へ持ち込まない | 圧縮が効きすぎない絵と音にする |

一括実用検査は 1,406 候補を 1 周するため、入力生成は軽いほど結果が揺れない。一方、実用継続検査で単色の静止画や単一の正弦波を流すと、圧縮が効きすぎてエンコーダーの実力が測れない。継続検査のパターンには、色相が回る背景、横スクロールする縞、速度の違う矩形、移動するノイズタイルと、多重波形の対数掃引、振幅掃引、微小ノイズを入れてある。

計測時は、入力の用意にかかった時間（合成パターンの生成、ライブフレームの拡縮）を `processingMs` から差し引く。実際の録画では既にできているフレームが渡ってくるため、検査治具の都合をエンコーダーの実力に混ぜない。パターンはフレーム番号・サンプル位置から決まり、乱数にはシード付きの線形合同法を使うので、何度実行しても同じ列になる。

#### パターンの確認とサンプル

アプリ上の「合成パターンを確認」（既定は折りたたみ）で、検査と同じ生成コードから映像を再生し、音声を波形付きで確認できる。検査の実行中は停止する。

ファイル出力は [../samples](../samples) に置き、git 管理する。

```bash
npm run inspector:samples        # 生成しなおす
npm run inspector:samples:check  # 現在のパターンと一致しているか確かめる
```

- `video/compatibility.png`: 一括実用検査の 1 枚
- `video/sustained.png`: 実用継続検査の動き（APNG。ブラウザーで再生できる）
- `audio/*.wav`: 48 kHz / 16-bit
- `manifest.json`: 生成条件と、圧縮前の生データの SHA-256

書き出しは [../scripts](../scripts) の Node.js スクリプトが `zlib` だけで PNG / APNG / WAV を組み立てる。`--check` は生データのハッシュだけを比較するので、zlib の実装差で圧縮済みファイルのバイト列が変わっても誤検出しない。Canvas 側と Node 側で同じ画素になるよう、描画命令は整数座標の矩形塗りとタイルの等倍貼りに限り、色は RGB の整数として持つ。

### キャプチャ音声

共有ダイアログで音声を共有すると、音声候補もキャプチャした実音声で検査できる。共有しなかった場合、音声候補を選んでいると `live-capture-audio-track-unavailable` で止まる。

`AudioEncoder` は設定どおりのサンプルレートとチャンネル数の `AudioData` しか受け取らない。そのため、[../workers/liveAudio.ts](../workers/liveAudio.ts) がチャンネルの割り当てと線形補間のリサンプルを行う。これは音質変換ではなく、環境が異なっても検査を実行できる形へ合わせるための処置である。

エコーキャンセル・ノイズ抑制・自動ゲインは要求時に切る。これらはモノラル前提で音声トラックを 1ch に落とすことがあるためである。実際のチャンネル数は `getSettings()` で結果へ残す。2ch 候補を 1ch のキャプチャで通した場合は複製して入力形状を合わせるが、`live-audio-captured-as-mono` を警告として記録する。この成功は 2ch を実際に扱えた証拠にはならない。

## 結果の読み方

### 実行と基本操作

```bash
npm run dev
```

`http://localhost:5173/encoder-capability-inspector/index.html` を開き、「一括実用検査を開始」する。

- 結果は検査終了を待たず、候補が完了するたびに一覧へ積まれる。
- 「検査を一時中断」で停止し、「途中から再開」で残りの候補から続けられる。
- 実用継続検査の中断には再開機構がない。完了済みの結果だけが残る。
- 「結果を破棄」で保存済みレポートを消す。
- 候補間の待機は既定 0 ms。0 のときはタイマー自体を張らない。
- UI は日本語と英語に対応し、初期表示はブラウザーの言語設定から決まる。

### 一覧、詳細、フレーム予算

一覧はコーデック、Profile / Level、bitrate mode、ハードウェア方針またはチャンネル数、各段階の成否、詳細、フレーム予算、継続検査、時間を示す。`quantizer` ではビットレートではなく比較用 QP を表示する。列見出しは絞り込みと並べ替えを兼ねる。並べ替えは昇順、降順、解除の順に巡回し、解除すると「新しい候補が先頭」の既定順へ戻る。

実用継続検査列の「100% 超 / 100% 以下」の絞り込みは、未実施候補を含めない。未実施を予算比 0 として扱うと、「100% 以下」に混ざってしまうためである。映像・音声を区別できるよう、ファミリー列には種別のアイコンを添える。

詳細列の失敗・警告は、ワーカーが返したコードとその説明を 2 行で示す。コードは環境をまたいで報告・検索できるため、訳文だけに置き換えない。未知のコードやデコーダーの生メッセージ、タイムアウトはそのまま表示する。

一括実用検査は 2 フレームだけの互換性確認なので、フレーム予算比には初期化コストがそのまま乗る。**100% を超えていても実用上の問題を意味しない。** 継続的な性能は実用継続検査の値で判断する。

`no-preference` の実際の実装は同じ codec string の `prefer-hardware` / `prefer-software` の出力を突き合わせて推定する。推定は確定情報ではない。

WebCodecs は実際に使われた実装を返す API を持たず、`isConfigSupported` の返却値だけからも分からない。合成入力は決定的なので、実装が同じなら出力バイト数とチャンク数も一致する。両方の方針が成功して出力が割れる場合、または一方が失敗し他方と出力が一致する場合は、一致した方を実体とみなす。出力が一致しなければ別の実装、両方の出力が同じなら方針を変えても実装が変わらなかった可能性があり、どちらも推定しない。この推定は合成入力の一括実用検査の結果だけに限る。

### ファミリー要約と書き出し

ファミリーで一律に可否を決めず、具体的な設定のうち何件が通ったかを数える。映像は codec string × bitrate mode 単位で数え、ハードウェア方針が違っても 1 件とする。音声は Profile・チャンネル数・bitrate mode を含む候補単位で数える。AAC は要求した codec string と、実出力の `decoderConfig.description` に含まれる AudioSpecificConfig の Audio Object Type が一致して初めて成功とする。宣言上の受理だけでは、要求した Profile を実際に出力できた証拠にならないためである。

## ビットレートの読み方

各結果の「検査」は、その候補を実エンコードした設定値である。`constant` / `variable` の映像ビットレートは YouTube の H.264、Apple の HLS、Google の VP9 設定表にある解像度別の初期目標を対応付けた。HEVC は Apple の HLS 初期目標を使う。AV1 / VP8 は一律の公式表がないため、VP9 の Web 配信表または WebM の例を比較起点にしている。これらは Level の規格上限や録画の推奨値そのものではない。`quantizer` は各 codec 登録仕様の QP 範囲から選んだ比較用値で、ビットレートは指定しない。

「ビットレートガイド」は、仕様・公式実装で確認できるサポート値と、公式配信ガイドや RFC の推奨値を、ファミリー / Profile / Level ごとに一覧する。codec string 横の情報ボタンと画面下部の全体一覧は同じカタログを参照する。全体一覧は表示範囲だけを描画する仮想スクロールと、ファミリー・codec string・Profile / Level の絞り込み、各列の昇順・降順・解除の並べ替えに対応する。WebCodecs にはブラウザーが受け付けるビットレート範囲を照会する API がないため、ガイドの値はこの環境の可否を保証しない。Windows Chromium の AAC 離散値は同 OS の公式実装に限った情報であり、macOS Chromium / macOS Safari は AudioToolbox の設定依存として別表示する。各結果の「検査」は実際に渡した代表値で、ガイドのサポート値・推奨値とは別に表示する。

「結果を JSON で保存」は全結果と実行環境の概要を出力する。`previousCompleted` は二重に含まれるため出力しない。画面内容、音声サンプル、デバイス固有 ID はレポートに含めない。一方でブラウザー、OS、GPU の概要は含むため、共有時には留意する。

結果は JSON として書き出せる。保存・書き出し対象は設定値、成否、計測値、環境の概要だけであり、画面内容、音声サンプル、デバイス固有 ID は含めない。
